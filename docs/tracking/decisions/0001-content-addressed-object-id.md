# 0001. 객체 id를 내용 해시로 정한다

## 맥락

원장은 여러 에이전트가 동시에 쓰고, 한 번 쓴 객체를 고치지 않는다. 초기(ledger 1) 객체는 UUIDv7 id를 썼고, 무결성 검사는 본문 sha256만 봤다. 이 방식에서는 제목·작성자·인용 같은 프런트매터를 바꿔도 검사에 걸리지 않고, 같은 내용을 두 번 발행하면 id가 다른 두 객체가 생긴다.

## 결정

새 객체(ledger 2)의 id를 `sha256(canonicalCore)`로 한다. canonicalCore는 id와 본문 해시를 뺀 모든 태생 필드(발행 시각·작성자 포함)를 고정 순서로 적고 본문을 붙인 바이트다. id가 곧 주소이자 무결성 증명이 된다. 저작 런타임·비용 정보(`authoring`)는 같은 주장에 대한 부수 관찰이라 코어에서 뺀다.

## 대안

- UUIDv7 id 유지: 시간순 정렬은 쉽지만, 메타데이터 변조를 잡지 못하고 같은 내용이 다른 id로 중복된다. 구 객체는 이 형식으로 남아 있고, `LedgerMigration`이 위상 정렬로 참조 대상부터 재해시해 옮기는 변환을 제공한다.
- `authoring`을 코어에 포함: 같은 지식을 다른 비용으로 쓰면 다른 객체가 되어 중복이 생기므로 택하지 않았다.

## 결과

- `verify`가 64자 id 객체의 코어 재해시를 검사해 본문뿐 아니라 메타데이터 변조도 잡는다.
- 같은 바이트의 재발행은 멱등이 되고, 같은 id에 다른 바이트가 오면 발행이 실패한다.
- `coreLines()`의 필드 구성·순서·표기는 사실상 고정된다. 바꾸면 기존 객체 전체가 코어 변조로 보고된다.
- UUIDv7 id와 64자 id가 한 world에 섞일 수 있고, 코드는 `isContentID`로 둘을 구분해야 한다.
